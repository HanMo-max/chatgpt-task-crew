## 对分工的判断

Luna 适合文件定位、调用链核对、边界清楚的实现和必要验证。主控可以保留方案、依赖和集成，减少常规执行占用主上下文。
近期案例证明这套角色组合确实使用过；不能据此计算长期调用占比、额度节省、速度提升或返工变化。
也没有证明整理后的模板已在一个全新目标客户端完成安装和真实子代理路由。

更强主模型不应成为“必须自己做所有执行”的理由；另一方面，主模型已经能一步完成的琐碎操作也不必为了形式另起一个子 Agent。
独立简单任务直接选择 Luna，复杂任务才使用主控加执行者的组合。并行收益来自独立工作流，不来自 Agent 数量本身。

## 上传内容与现行分工的对应关系

| 现行源方案 | 本仓库整理 | 原因 |
|---|---|---|
| Skill 包含委派门槛、工作流和升级规则 | 完整保留现行 Skill 原文 | 公开版本反映实际部署，不另造分工政策 |
| 多文件、探索或外部事实查询等触发强制派发 | 保留现行门槛及琐碎任务豁免 | 不机械启动全部角色；用户明确指令优先 |
| 主控 Astra 默认，兼容 Sol；普通子代理 Luna | 保留默认与用户选择，运行时另行核对 | 配置不冒充本次实际模型 |
| 并发上限 6 | 保留上限 6 | 与本机现行配置一致，运行时名额可能更少 |
| Astra 主控下经用户授权派发 Sol high；Sol 主控下自行接管 | 保留现行双支路协议与可见性要求 | 升级和接管分别处理，已有同类授权不重复询问 |
| 项目内业务角色和正式职责约束 | 仅提取可移植任务分工 | 不把私有业务规则和资料带入公开仓库 |
| 角色名容易被当作模型证据 | 请求、启动、子会话元数据、任务结果分别核对 | 角色存在与模型生效是不同证据 |

主配置、五个角色 TOML 和 Skill 共七个文件与本机现行部署逐字节一致，SHA-256 见 [deployment-manifest.json](deployment-manifest.json)。`AGENTS.md` 是分工规则摘录，安装、示例和复盘为补充文档；没有复制原项目完整业务治理文件，也没有回写原项目配置或决策。

## 现行规则的适用边界

现行 Skill 的委派门槛较宽，例如仓库探索或外部版本事实核对本身也可能触发实际委派。它同时排除琐碎任务，并要求不机械启动所有角色。本仓库按用户要求保留这些现行规则，没有把观察到的改进建议当作已经部署的修改。

`gpt-6.1-sol` 主控下的近期模型分工有真实使用证据；但现行 Skill 升级协议原文仅列 `gpt-6-astra` 和 `gpt-6-sol`，未明确覆盖 `gpt-6.1-sol` 的受阻支路。此处保留并披露这一范围，未静默新增模型支路。

## 本仓库验收范围

静态检查核对 TOML、五个角色的模型和权限默认值、Skill 名称及仓库内链接，并对 UTF-8 文本做有限的私人路径/凭据模式扫描；这不能代替完整的敏感信息审计。
Skill 的前置信息检查与七个现行文件的来源一致性检查已通过。静态脚本不调用外部模型服务，也不证明其他目标客户端已经加载模板。
其他目标客户端安装与端到端路由验证仍需按 [runtime-verification.md](runtime-verification.md) 执行。

## 与官方能力的关系

官方文档说明项目级自定义 Agent 可放在 `.codex/agents/`，并可声明模型、推理强度及权限默认值；全局子 Agent 默认位于 `[agents]`。
自定义角色、显式派发值、默认值、父会话配置和实时权限覆盖共同影响有效行为，因此需要观察真实调用。

参考：[官方子 Agent 配置说明](https://learn.chatgpt.com/docs/agent-configuration/subagents)。
